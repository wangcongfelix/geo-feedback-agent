# GeoFeedback Agent 面试演示脚本

这份脚本面向 2 到 3 分钟求职演示，重点讲清楚业务问题、产品流程、AI 边界和评测态度。

## 3 分钟精简版

### 0:00-0:25 业务背景

“GeoFeedback Agent 是一个面向地图、导航、航旅、智能交通和 GIS 产品经理的反馈整理工作台。地图类反馈经常来自客服、应用商店、访谈和项目现场，表达很散，Bug、数据问题、需求和操作问题混在一起，也经常缺少设备、版本、地点和复现信息。这个工具的目标是把一批非结构化反馈整理成可筛选、可审核、可导出的结构化清单。”

### 0:25-1:10 单条诊断与人工审核

“我先演示单条模式。这里输入一条反馈，也可以补充产品类型、设备版本和地点。点击诊断后，AI 会给出产品模块、问题类型、处理优先级、置信度、待补充信息和不确定性。AI 只是预填建议，产品经理在这里做卡片式审核，可以编辑少数字段，也可以一键接受全部 AI 建议并确认。”

### 1:10-1:35 问题单生成

“确认后才会进入问题单生成阶段。这里可以选择 Bug 单、数据问题单或产品需求单。正式问题单不是再次调用 AI，而是用 TypeScript 模板根据人工确认后的 reviewedDiagnosis 生成，所以不会把未经确认的 AI 原始结果直接交给研发。”

### 1:35-2:20 批量反馈总表

“批量模式可以一次粘贴多行反馈，当前最多 20 条。系统会按顺序逐条调用模型，单条失败不会中断整个批次。诊断完成后进入反馈总表，可以按产品模块、问题类型、审核状态和待人工判断筛选，也可以对没有修改过的记录批量接受 AI 建议。”

### 2:20-2:40 导出

“导出有两种方式：反馈总表可以直接下载 CSV；在 Chrome、Edge 等支持 File System Access API 的浏览器里，也可以选择文件夹，把反馈总表和已生成的问题单一起写入本地目录。如果浏览器不支持或权限不足，会降级为普通下载，网页不会绕过浏览器权限直接写电脑目录。”

### 2:40-3:00 评测与总结

“我为 Prompt V1 做过 15 条人工设计 Golden Set 的历史基线：模块分类 13/15，问题类型 15/15，格式合规 15/15，平均接口处理耗时 8.52 秒。V2 尝试修复 Badcase，但回归测试发现问题类型准确率下降，所以正式 Demo 继续使用稳定 V1。这个项目的重点是 AI 做初步整理，产品经理做最终判断，结果可审核、可导出、可评测。”

## 0:00-0:30 业务问题

可以这样说：

“这个项目叫 GeoFeedback Agent，是一个面向地图、导航、航旅、智能交通和 GIS 产品经理的反馈整理工作台。地图类产品经理经常会收到客服转述、应用商店评论、用户访谈、群聊和项目现场反馈，这些内容很零散，Bug、数据问题、需求和操作问题混在一起，还经常缺少设备、版本、地点和复现信息。

我的目标不是让 AI 直接替产品经理做决策，而是先把这些非结构化反馈整理成可审核、可筛选、可导出的结构化清单，再由产品经理确认后生成标准问题单。”

## 0:30-1:05 演示单条反馈

操作：

1. 进入单条反馈模式。
2. 输入一条地图或导航反馈，例如“打开地图后一直白屏”或“导航一直让我走已经封闭的路”。
3. 可选择填写产品类型、设备、版本、地点等补充信息。
4. 可选择一张截图。
5. 点击开始诊断。

可以这样说：

“这里保留了产品经理真实工作里的上下文字段，但只有原始反馈是必填。截图当前只作为证据附件保留，不上传服务器，也不传给模型做图片分析。”

## 1:05-1:25 演示 AI 初步诊断

操作：

1. 展示 AI 诊断摘要。
2. 指出产品模块、问题类型、处理优先级、置信度、Prompt 版本和模型供应商。
3. 展开“查看 AI 分析依据”。

可以这样说：

“AI 会先给出结构化诊断，包括产品模块、问题类型、处理优先级、用户明确事实、AI 推测、待补充信息和不确定性。这里我刻意把 AI 依据放在折叠区，避免它和人工审核区重复占据太多页面。”

## 1:25-1:50 演示卡片式人工审核

操作：

1. 展示产品经理审核区。
2. 点击某个卡片的编辑按钮，展示可修改字段。
3. 如果不需要修改，点击“接受全部 AI 建议并确认”。

可以这样说：

“这是 Human-in-the-loop 的关键环节。AI 结果只是预填建议，产品经理可以逐项修改，也可以一键接受。修改过的字段会被记录下来。只要人工审核内容发生变化，确认状态会回到审核中，已经生成的问题单不会继续沿用旧结果。”

## 1:50-2:10 演示问题单生成

操作：

1. 在确认后展示问题单生成区。
2. 选择 Bug 单、数据问题单或产品需求单。
3. 生成 Markdown。
4. 展示复制、下载和结构化 JSON。

可以这样说：

“正式问题单不是再次调用 AI 生成的，而是由 TypeScript 模板确定性生成。这样可以保证问题单使用的是人工确认后的 reviewedDiagnosis，而不是 AI 原始 diagnosis。”

## 2:10-2:35 演示批量输入 5 条反馈

操作：

1. 切换到批量反馈模式。
2. 粘贴 5 行反馈，每行一条。
3. 点击开始批量诊断。
4. 展示顺序处理进度。

可以这样说：

“批量模式最多处理 20 条。这里没有做队列系统或数据库，所有状态保存在当前浏览器页面内存里。请求是顺序执行的，每条之间有等待，避免演示时触发模型接口限流。单条失败不会中断整个批次。”

## 2:35-2:55 演示反馈总表、筛选和导出

操作：

1. 展示批量反馈总表。
2. 用产品模块、问题类型、审核状态或待人工判断筛选。
3. 批量接受 AI 建议。
4. 下载反馈总表。
5. 选择文件夹并导出全部。

可以这样说：

“批量总表是给产品经理快速扫一批反馈用的，所以只展示产品模块、问题类型、处理优先级、置信度、待补充信息和状态。详情、AI 推测和实际预期结果放在单条详情里。导出时可以直接下载 CSV，也可以选择文件夹，把反馈总表和已生成的问题单一起保存。”

## 2:55-3:15 评测和 V2 回归

如果时间允许，可以这样说：

“我为 Prompt V1 做过一版 Golden Set 评测，测试集是 15 条人工设计案例。历史基线是：模块分类 13/15，86.67%；问题类型 15/15，100%；格式合规 15/15，100%；平均接口处理耗时 8.52 秒；人工复核后明确信息虚构率 1/15，字段级人工修改率 22/165，13.33%。

我也做过 V2 实验，尝试修复模块边界和推测边界问题，但回归测试发现问题类型准确率下降。所以 Demo 仍然使用稳定的 V1，没有把失败结果藏起来。”

## 结尾

可以这样说：

“这个项目的价值不在于让 AI 自动替代产品经理，而是把 AI 放在一个可审核、可回滚、可评测的产品工作流里。AI 做初步整理，产品经理做最终判断，系统负责把确认后的结果变成可交付的问题清单和问题单。”
