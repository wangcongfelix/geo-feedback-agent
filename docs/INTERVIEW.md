# GeoFeedback Agent 面试问答

## 1. 为什么选择这个项目？

我想做一个既能体现 AI 产品能力，又和地图/GIS 业务经历有关的项目。地图类反馈不是简单文本总结，里面会混合 Bug、数据问题、需求、操作问题和大量缺失信息，很适合展示产品经理如何把 AI 放进真实工作流，而不是只做一个聊天框。

## 2. 用户是谁，解决什么痛点？

核心用户是地图、导航、航旅、智能交通和 GIS 产品经理，也包括客服、运营和项目实施人员。痛点是反馈来源很散，表达不统一，缺少设备、版本、地点、复现步骤，不能直接交给研发或数据团队。这个项目帮助他们先把反馈整理成结构化清单，再人工确认重点问题。

## 3. 为什么需要 AI，而不是普通规则？

普通规则适合处理确定性任务，比如 CSV 导出、问题单模板、状态流转和字段对比。但用户反馈是自然语言，表达非常口语化，同一句话里可能同时包含场景、现象、情绪和隐含需求。AI 更适合做初步理解和结构化提取，比如判断模块、归纳问题、提取用户事实和识别待补充信息。

## 4. 为什么又加入确定性 Guardrail？

因为不是所有判断都应该交给模型自由发挥。比如“打不开、白屏、崩溃、一直加载”已经明确描述功能异常，如果模型仅因为缺少设备或版本就输出“信息不足”，会影响产品经理分拣效率。所以我加入轻量 Guardrail，给模型补充内部判断上下文，同时不直接改写模型输出根因，也不自动指定优先级。

## 补充：当前正式产品如何处理“信息不足”？

这里要区分历史评测和当前页面策略。Prompt V1 的 Golden Set 里包含“信息不足，暂时无法判断”，这是为了评估模型在上下文不足时能不能承认不确定。当前正式产品页面会尽量给出最可能的问题类型，不把“信息不足”作为最终展示分类。

比如用户只说“这个不好用”，页面会归为“使用体验或操作问题”，同时把置信度设低，保留待补充信息和不确定性说明。这不代表 AI 一定能准确判断所有模糊反馈，而是避免最终表格里出现一个无法行动的分类，再把不确定性留给产品经理审核。

## 5. 为什么不能让 AI 直接生成正式问题单？

正式问题单会进入研发或数据处理流程，里面的模块、类型、优先级和实际预期结果都可能影响排期和责任归属。AI 可以整理草稿，但不能成为最终决策者。所以系统要求产品经理确认后才能生成问题单，并且问题单只使用人工确认后的 reviewedDiagnosis。

## 6. Human-in-the-loop 怎么实现？

前端保留两份对象：AI 原始诊断 diagnosis，以及产品经理审核后的 reviewedDiagnosis。审核区默认用 AI 结果预填，产品经理可以编辑卡片，也可以一键接受 AI 建议。系统会用字段级比较记录 modifiedFields。只要审核内容再次变化，状态就回到 reviewing，问题单区域隐藏，需要重新确认。

## 7. 批量处理的数据流是什么？

批量模式中，用户把多行反馈粘贴进文本框，一行作为一条反馈。前端忽略空行，最多取 20 条，生成内存中的 FeedbackRecord。点击开始后，前端按顺序调用 `/api/diagnose`，每条之间等待，单条失败只记录失败状态，不中断后续反馈。诊断成功后进入总表，用户可以筛选、选择、批量接受 AI 建议，再生成和导出问题单。

## 补充：导出为什么有兼容性说明？

因为网页不能绕过浏览器权限直接写入用户电脑的任意目录。Chrome、Edge 等支持 File System Access API 的浏览器，可以在用户主动选择文件夹并授权后，写入反馈总表和问题单文件。如果浏览器不支持这个 API，或者用户没有授权目录写入，系统会降级为普通下载。

## 8. 为什么不做数据库？

这是求职演示 MVP，目标是验证反馈整理、人工审核、问题单生成和评测闭环。数据库会带来登录、权限、历史记录、数据清理和部署复杂度，但不会直接证明核心产品判断。所以当前数据只保存在浏览器页面内存中，导出靠 CSV 和 Markdown 文件完成。

## 9. Golden Set 如何设计？

Golden Set V1 是 15 条人工设计的 synthetic_test_case，不声称是真实用户反馈。它覆盖 Bug、地图或业务数据问题、产品需求、使用咨询或操作问题、信息不足，也覆盖搜索与 POI、地图展示、路线导航、定位轨迹、离线地图、航旅信息、账号同步和 B 端 GIS 平台等模块。这里的“信息不足”是 Prompt V1 历史评测里的标准答案之一，不等同于当前正式页面的最终分类展示。对有合理多解的案例，会记录歧义说明。

## 10. 如何计算模块准确率和格式合规率？

模块准确率是模型预测 productModule 与人工标注 expectedProductModule 一致的案例数除以总案例数。Prompt V1 的历史结果是 13/15，86.67%。格式合规率是接口返回能否通过 JSON 解析和 Zod Schema 校验，V1 在这 15 条案例中是 15/15，100%。

## 11. 信息虚构率如何人工判断？

信息虚构率不是脚本自动判断的。自动评测会保存模型完整输出，然后人工检查 userFacts、evidenceQuotes、aiInferences 等字段，看是否把用户没有提供的信息写成确定事实。V1 人工复核中，15 条里有 1 条明确虚构用户身份，因此记录为 1/15，6.67%。

## 12. V2 为什么出现回归？

V2 加了更多规则，主要想修复 V1 的模块边界、推测边界和备选类型问题。但规则变多后，模型在部分案例上的问题类型判断变得不稳定，回归测试发现问题类型准确率下降。这说明 Prompt 不是越长越好，局部修复可能引入副作用。

## 13. 为什么没有继续做 V3？

因为项目目标不是堆出很多版本，而是展示可评测、可复盘的产品迭代方法。V2 已经出现回归，在没有更大样本和更明确 Badcase 分析前，继续做 V3 很容易变成凭感觉调 Prompt。所以我选择保留 V1 作为稳定 Demo，把 V2 作为实验分支记录下来。

## 14. 项目当前最大的不足是什么？

最大不足是评测集还小，只有 15 条人工设计案例，不代表生产环境表现。其次，当前没有真实团队使用数据，也没有长期保存和协作能力。截图也只是附件名称记录，没有做图片理解。作为 MVP，它能展示工作流和评测方法，但还不是生产级系统。

## 15. 如果真正上线，下一步做什么？

我会先扩大 Golden Set，引入脱敏真实反馈，并按模块和问题类型分层评测。然后补充持久化、权限、历史记录和团队协作。等核心分类和审核流程稳定后，再考虑相似反馈聚类、工单平台集成和截图 OCR，但不会一开始就做复杂平台化。

## 16. 你作为产品经理具体做了什么？

我做了业务场景定义、用户流程设计、分类体系设计、AI 与人工边界设计、问题单模板设计、Prompt 评测指标设计和 Badcase 复盘。工程上也实现了页面、API、Schema、导出和评测脚本，但我更想强调的是：这个项目不是单纯调接口，而是围绕产品经理工作流设计 AI 应用。

## 17. 哪些部分使用了 Codex，哪些决策是你做的？

我使用 Codex 辅助完成代码实现、文件整理、评测脚本和文档生成。但项目方向、用户痛点、地图业务分类、Human-in-the-loop 原则、是否保留 V1、如何解释 V2 回归、哪些功能不做，都是我根据产品目标做的决策。Codex 是实现和协作工具，不替代产品判断。

## 18. 如何证明项目不是简单套壳？

第一，它不是一个通用聊天界面，而是完整的反馈整理工作台。第二，它有地图业务分类、Schema、人工审核、问题单模板、批量表格和导出流程。第三，它有 Golden Set、自动评测、人工复核和 Badcase 记录。第四，它明确说明技术骨架参考 OpenAI Structured Outputs Sample，但地图业务和产品流程是独立设计。

## 19. 如何保护用户反馈数据？

当前 MVP 不使用数据库，反馈只保存在浏览器内存中，刷新后会消失。模型调用只发生在服务端，API Key 不进入浏览器。截图不上传服务器，也不传给模型。真正上线前，需要增加脱敏提示、数据保存策略、权限控制、审计日志和企业数据合规评估。

## 20. 这个项目与你的 GIS 和地图产品经历有什么关系？

地图/GIS 反馈有很强的业务特征，比如 POI、图层、路线规划、定位、轨迹、离线包、SHP/GeoJSON 文件、航班和实时交通信息。这个项目把这些场景抽象成产品模块和问题类型，并把用户反馈整理成研发或数据团队能继续处理的问题单，所以它和地图产品经理的实际工作非常贴近。
